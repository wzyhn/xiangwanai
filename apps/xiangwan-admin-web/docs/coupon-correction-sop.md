# 优惠券异常人工处理

签到撤销后的 `correction_required` 是历史异常标记，原券不再可用。人工处理单独追加事件，不覆盖券、报名、订单或支付历史，也不执行外部转账。人工补发五券不能代替异常结案；签收发券策略见 [coupon-policy.md](coupon-policy.md)。

1. 租户超级管理员在 `/coupon-corrections` 查看关联订单、报名与券面额，填写核查说明并“开始处理”。
2. 已预占但未核销的券先完成正常订单取消/过期及释放，等待撤销签到的冲正流程追加失效事实。另一名超级管理员确认从未核销、当前账本已失效，以工单引用、零金额及核查说明登记权益结案。仍预占的券不能结案。
3. 曾核销的券由客户在其财务系统处理异常折扣；另一名超级管理员核对可复查的官方最终调整记录，再登记财务凭证引用、核查说明及等于券面额的金额（整数分）。部分金额、口头确认或处理中记录不能作为结案依据。系统不据此修改订单实付或生成渠道退款。
4. 经办人和结案人必须是不同的超级管理员。每个写操作需要 UUIDv4 操作键和版本；服务端在可串行化事务内重验实时身份、权限、代际、版本和账本，处理事件、回执与审计一起提交。事件禁止更新、删除和清空。
5. 网络结果不明时保留本会话的原请求，刷新后“原样重试”。金额保持字符串，不经浮点数转换。浏览器无法保存恢复记录时不发请求；明确拒绝后刷新状态并重新核对。引用和说明不得包含联系人等个人信息；列表和写回执仅返回处理元数据。

这是 V1 工程默认流程，采用双人复核和完整金额。客户仍需配置真实 OIDC 管理员、外部财务凭证系统与责任人，并在客户库完成上线验证。本地真实 PostgreSQL 测试使用合成业务数据，不证明外部财务调整已发生。
