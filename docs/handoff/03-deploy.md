# 复制给 AI：更新享玩服务器

我授权你对我拥有的享玩服务器完成本次项目发布。可以修改整个享玩项目、调整其部署配置和运行服务，使用交接包 private/mcp.json 从本地读取 Coolify 凭据。真实凭据不得进入公开 GitHub、issue、PR、聊天输出和公开日志。按下面步骤实际执行，遇到可排查问题自行解决。

1. 读取交接包私下的服务器盘点与授权，连接 MCP，先使用 coolify_help、get_current_team、search_resources/list_resources 核对实际团队、资源 UUID、域名与资源类型。初始盘点 UUID 是线索，当前查询结果才是操作依据。MCP 工具未覆盖操作时，可以从同一本地文件加载令牌调用实例 /api/v1 REST；先核对官方接口契约，固定目标实例，不向其他站点发送令牌，不输出完整环境值。
2. 查清现网究竟从 Git 仓库构建，还是从已有镜像启动；记录当前 Git SHA、镜像 tag/digest、API/Admin/worker 版本、数据库迁移体系、挂载、域名和回调路径。只有名字相似不足以认定资源。一次性 migrate/bootstrap 退出不等于故障；持续重启需要查原因。不要把空库独立初始化用于现有平台数据库。
3. 本次要发布的源码必须来自已接受的公开 main 完整 SHA，或我明确指定的测试分支。核对这个 SHA 的 CI 和本地必要检查。公开 CI 目前没有镜像推送/生产部署步骤；如果现网用镜像，先从这个源码构建并发布 API、迁移器、后台镜像到服务器可访问的仓库，固定不可变 tag 与 digest，然后更新目标资源。不能重启旧镜像后称已发布新代码。若建立持续发布流水线，部署令牌留在受保护的部署环境；外部 PR 的 CI 不获得生产秘密。
4. 后台生产构建必须指定 XIANGWAN_ADMIN_API_ORIGIN，并核对 API 的实际路由与 OIDC 同源回调。构建 API 用根 Dockerfile 的 xiangwan target；独立新库迁移工具用 xiangwan-migrate target；后台用 apps/xiangwan-admin-web/Dockerfile。API、worker 和 migrate 的版本要相容。
5. 部署前取得可以恢复的数据库与媒体备份，记录上一组镜像 digest，比较目标配置与现网配置。现有 tenant/generation、AppID/商户绑定、OIDC、媒体卷和密钥挂载从现网核实，不能生成另一套替换现有身份。必要变更按现有迁移体系前滚；不清空业务表、重建数据库或删媒体卷。
6. 用 MCP/REST 执行这次发布；超时或返回不明时查原 deployment UUID 和状态，避免重复触发。顺序按实际数据库迁移、API/worker、Admin 依赖安排。需要访问服务器时使用服务器所有者的登录身份，凭据只保留在本机；压缩包不包含 SSH 私钥。
7. 等待部署终态，核对运行容器的新 digest、/ready、首页、往期页、Admin 登录/内部页面，抽查本次修改链路。后台首页配置需要先发布才会有首页数据。微信登录、支付拉起、支付查询、取消与退款分别记录真实验证结果；需要真机或资金操作时使用所有者明确提供的测试身份和单笔测试计划，不能用健康检查代替支付验收。
8. 若新版本失败，恢复上一组可运行镜像与配置；schema 用前滚修复，不能盲目执行 down.sql。完成后报告源码 SHA、镜像 digest、deployment UUID、域名和验收结果，列出实际未验证项。

公开修改回到私有平台另有受限集成流程；我没有平台访问权限时不去拉私有 weconq。若发布享玩独立服务器已完成，只报告这一部署事实。微信体验版/正式版需开发者身份与发布验收，服务器部署不会自动上传小程序。
